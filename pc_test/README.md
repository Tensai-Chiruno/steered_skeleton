# pc_test —— 主机端验证台

**这不是固件的一部分。** 这里的代码不接硬件、不进任何一板的 CMake 构建，只做一件事：
在电脑上先把纯数学/纯逻辑的部分验证掉，把宝贵的上板时间留给真正需要硬件的部分。

## 跑起来

```bat
pc_test\build_and_run.bat
```

脚本会自动定位 MSVC（优先 `vswhere`，回退到 BuildTools 默认路径），用
`/std:c++17 /utf-8 /O2 /W4` 编译并运行。退出码 0 表示全部通过。

## 当前覆盖：`test_pid.cpp`（考核第 4 项）

被控对象用一阶惯性环节近似（时间常数 50 ms），步长固定 1 ms，与 `htim6` 主任务同频。

| 用例 | 证明什么 |
|---|---|
| 1. 纯 P 阶跃 | 稳态误差必然存在（3.333 / 目标 10）→ 这就是需要 I 项的理由 |
| 2. PI 阶跃 | 稳态误差降到 1e-5，超调 < 30% |
| 3a. 饱和 + 误差同向 | **条件积分抗饱和**生效：连续 1000 拍饱和，积分仍是 0（不是"被限幅"，是被拒绝） |
| 3b. 不饱和 | `integral_limit` 把积分项钉在 5.000；不限幅时 2000 拍长到 20.000 |
| 4. 角度回绕 | +179° 对 -179°：回绕后误差 **-2°**，不回绕是 **+358°**（会几乎转一整圈） |
| 5. `dt <= 0` | 保持上一拍输出，不产生巨大微分（`GetTickMs` 49.7 天绕回时会遇到） |
| 6. 未 `init` | 增益全 0 → 输出恒 0（失效安全：忘记初始化是"不动"而不是"乱动"） |

最近一次运行：**12 passed, 0 failed**。

### 用例 4 的符号，值得记一笔

`+179° − (−179°) = +358°`。而 `−179°` 等价于 `+181°`，**其实已经越过目标 2°**，
所以回绕后的正确结果是最短路径 `−2°`。写测试时我一开始把期望值写成了 `+2°`
和 `−358°`，两个符号都反了——`pid.hpp` 的行为是对的，是测试写错了。
同一处注释原本也把符号写反，已一并订正。

## 后续要往这里加什么

按依赖顺序，任何"能在电脑上判定对错"的东西都应该先落在这一层：

1. **舵向轮逆解**（第 5 项）：喂 `(v_x, v_y, ω)`，检查四轮 `(θ, 轮速)`；
   重点验证 180° 二义性不会让舵角跳变、`ω=0` 时 `atan2(0,0)` 不产生乱跳
2. **双板协议**（第 9 项）：同一结构 `encode` 再 `decode` 应能还原原值
3. **状态迁移**（第 6 项）：喂遥控器拨杆序列，检查状态机是否按预期迁移

## 为什么放在这里而不是 `Chassis/`

`Chassis/CMakeLists.txt` 用 `src/*.c*` 递归 glob 收集源文件。把测试放进板级目录会被
编进固件，既占 flash 又可能引入 `main()` 重复定义。放 `pc_test/` 下则完全隔离，
且 `.gitignore` 里刻意没有忽略它——测试是**验证证据**，必须提交。
